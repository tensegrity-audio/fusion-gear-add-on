# Existing generators and Gear Studio's design decisions

Review date: **2026-09-16**. This is a bounded review of primary documentation and selected source references, not a live Fusion benchmark or an exhaustive market survey. Third-party documentation can establish what its author claims; it does not independently establish performance, accuracy or reliability. No competing add-in was executed for this review.

The goal is one consistent workflow for editable B-rep gears: broad individual-gear coverage, remembered successful settings, real expression inputs, validation before expensive work, and recovery when an update fails. Gear Studio's implementation status is separate from that goal. See [VERIFICATION.md](VERIFICATION.md) for completed checks and [ACCEPTANCE.md](ACCEPTANCE.md) for native Fusion tests still required.

## Where the opportunity is

Ordinary involute spur and helical generation overlap heavily. Coverage also extends well beyond those families in existing tools. Remembering recent settings is already documented by GF, and parametric model templates already exist. None of those features by itself is the project's distinguishing claim.

The opportunity inferred from this review is **consistent behavior across families**: the same expression conventions, saved definitions, update actions, validation standards, cancellation behavior and recovery rules. The reviewed sources did not establish one tool that combines all of those properties across the desired coverage. That is a gap in demonstrated coverage, not proof that no other implementation exists.

Gear Studio does not yet close the entire gap. It implements 13 individual variants with a shared edit/update path, but native Fusion acceptance remains pending; automatic recomputation, paired-gear validation and assembly solving remain future work.

## Decisions carried into this code

| Decision | Reason and implementation |
| --- | --- |
| B-rep solids as the deliverable | The output must support Fusion solid workflows. The builder prepares a detached `BRepBody` and verifies one closed solid before commit. A setup preview is not an exported polygon mesh. B-rep representation does not imply exact mathematical profiles; spline and envelope approximations are documented. |
| Real user parameters with explicit regeneration | Parameter rows supply expressions used by **Update from Parameters**. They are not decorative snapshots, but changing them alone does not update the solid. Each gear stores its expression definition and parameter mapping. |
| Stable API before automatic custom-feature recomputation | Autodesk still labels Custom Features as preview and advises against delivering applications that depend on preview capabilities. This release uses an explicit update command rather than promising a production-stable custom compute event. [Autodesk Custom Features documentation](https://help.autodesk.com/cloudhelp/ENU/Fusion-360-API/files/CustomFeatures_UM.htm) |
| Update the owned source body | Autodesk's `BaseFeature.updateBody` copies a replacement definition into an existing source body while the feature is being edited. Gear Studio uses this mechanism to retain the owning feature and component. Individual tooth-face references can still change. [Autodesk method reference](https://help.autodesk.com/cloudhelp/ENU/Fusion-360-API/files/fusion_BaseFeature_updateBody.htm) |
| Validate, prepare, then commit | Cheap dimensional/dependency checks precede native geometry. A temporary design isolates preparation; commit rechecks inputs and attempts recovery if the host rejects the update. Tests with substitutes exercise this logic; live host behavior still needs acceptance. |
| Bounded work and cooperative cancellation | Numerical loops and feature boundaries check work budgets and cancellation. A single synchronous Fusion kernel operation cannot be forcibly stopped by those checks. “Never hangs” is not an honest absolute guarantee. |
| Separate defaults, presets and gear definitions | Last-used defaults advance only after success. Named presets are explicit. Per-gear definitions stay with the saved design. New templates expand source-owned aliases while retaining external expressions. |
| State the unit and backlash conventions | Normal module/pressure angle and per-gear tooth thinning are explicit. Bevel module uses the outer normal section. A future pair solver must convert pair-level clearance into member settings deliberately. |

Implementation details are in [ARCHITECTURE.md](ARCHITECTURE.md). The [roadmap](ROADMAP.md) places native verification before broader automation or more gear families. Comparisons should be revised when upstream evidence changes; keep the evidence date and distinguish documentation claims from measured results.
